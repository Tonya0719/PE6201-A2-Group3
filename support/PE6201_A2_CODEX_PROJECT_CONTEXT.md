# 2. Business task

This is **Problem A: health-insurance claim first response**.

One Agent run processes **one claim** from `data_A/claims.json`.

The Agent must produce exactly one of:

- `approve_in_principle`
- `request_document`
- `escalate`

This is not merely "pay / do not pay". It is first-response adjudication / triage:

- a claim can be approved in principle with some line items refused;
- missing documents or preauthorisation can lead to `request_document`;
- policy / duplicate / hostile-instruction conditions can lead to `escalate`.

The single irreversible / gated action is:

```text
issue_decision_letter
```

For A2 it must only write a **local structured record**. No real email, PDF, external claim system, database server, or UI is required.

# 3. Data model and how the files relate

## 3.1 `claims.json` is the work queue

`data_A/claims.json` contains the claims to process.

**One row = one Agent run.**

Example logical flow:

```text
claims.json
    ↓
run_agent(claim_id)
    ↓
Agent uses tools to query other local systems of record
```

## 3.2 The other JSON files are reference tables / systems of record

The Agent should not receive all data at once.

It should retrieve facts through tools from:

```text
data_A/
├── claims.json
├── members.json
├── policies.json
├── hospitals.json
├── procedures.json
├── preauthorisations.json
├── required_documents.json
└── decided_claims.json
```

Relationships:

```text
claim.member_id
    → members.json
    → policy_id
    → policies.json

claim.hospital_id
    → hospitals.json

claim.lines[].code
    → procedures.json
    → required_documents.json

member_id + procedure_code
    → preauthorisations.json

current claim facts
    → decided_claims.json
    → exact duplicate check
```

## 3.3 `make_fixtures_A.py`

This is the teacher-provided fixture generator.

It is used to create / regenerate `data_A/*.json`.

When adding evaluation cases:

- add **new rows with new IDs** to the `EXTRA_*` areas;
- run `python make_fixtures_A.py`;
- do not edit or delete teacher-shipped rows;
- do not treat the generated JSON as the primary editable source.

Conceptually:

```text
make_fixtures_A.py
    ↓
teacher rows + EXTRA_* rows
    ↓
data_A/*.json
```

## 3.4 `expected_outcomes_A.json`

This is the answer key / ground truth.

It is not generated by the Agent.

For each new evaluation case, the correct outcome must be written **by hand from the routing rules before looking at the Agent's answer**.

Conceptually:

```text
claims.json = question
expected_outcomes_A.json = correct answer
```

## 3.5 Evaluation harness

The harness:

```text
reads case
    ↓
runs Agent
    ↓
gets actual record
    ↓
reads expected outcome
    ↓
code check + judgement queue
    ↓
summary / results.json
```

The harness must not create the business answer itself.

## 6.5 `issue_decision_letter(...)`

Current signature:

```python
issue_decision_letter(
    case_id,
    decision,
    trigger,
    reason,
    evidence,
    missing_item=None,
)
```

Purpose:

- the only irreversible Agent-visible tool;
- append one local structured decision record;
- reject invalid decision values;
- require `missing_item` for `request_document`;
- require a trigger for `escalate`;
- block a second write for the same case.

State:

```text
in-memory OUTBOX
```

Important governance rule:

```text
AUTONOMY is system/runtime configuration.
The model must not be allowed to set autonomy.
```

# 9. Current prompt hardening — preserve this

A real live-model failure was observed:

The model returned, in one model call:

```text
Action
Observation (fabricated)
Action
Observation (fabricated)
Final
```

It invented fake policy IDs, preauthorisation IDs, and coverage results.

Therefore the current prompt/parser deliberately enforce:

1. one model call returns exactly one JSON object;
2. Action → STOP;
3. the model must never generate an Observation;
4. tool/system-of-record facts must never be invented;
5. facts not returned by the runtime are unknown;
6. multiple independent calls may only appear inside one `tool_calls` list;
7. JSON response format is requested for live OpenRouter calls when enabled;
8. parser rejects invalid/multiple JSON instead of silently extracting one part.

Do not weaken these constraints.

Current parser explicitly rejects:

```text
MODEL_FABRICATED_OBSERVATION
INVALID_OR_MULTIPLE_JSON
UNKNOWN_RESPONSE_TYPE
```

# 10. Current optimized turn design

The team's current design outline expects efficient paths.

Current interpretation in the ZIP:

```text
Intake
    get_claim
        ↓
Policy verification
    lookup_policy
        ↓
Line verification
    check_coverage × N
    get_preauthorisation × M
    + deferred helpers
        ↓
```

Current expected model-call trajectories documented by the project:

```text

policy-level escalation        ≈ 3 model calls

```

### Important teacher-alignment issue: definition of "turn"

The teacher scaffold treats **tool-calling turns** as turns and does not count final bookkeeping the same way.

The current code's `turns` variable is closer to **model invocations**.

This must be made explicit before D6/D7 reporting.

Recommended instrumentation:

```text
model_calls
tool_turns
```

Do not rely on one ambiguous `turns` number if the report compares to teacher examples.

Example duplicate:

```text
get_claim tool-calling round = 1 tool turn
next model invocation returns judgement/final

model_calls = 2
tool_turns = 1
```
